# Vulithuba

Vulithuba is a telecommunications website with a local Node.js API, SQLite database, email/SMS notifications, and a SwiftUI iOS app.

## Requirements

- Node.js 24 or newer
- Xcode 26 or newer for the iOS app
- Dependencies installed with `npm install`

## Run the website locally

```bash
npm install
./start-vulithuba.command
```

The website opens at <http://127.0.0.1:3000/index.html>.

The server loads configuration from `.env`. Copy `.env.example` to `.env` and add notification or payment credentials only on the server. Never commit `.env`.

## Password reset

Open <http://127.0.0.1:3000/forgot-password.html> while the local server is running. Request a new email and use the link generated by the local server. The reset link is valid for one hour and can only be used once.

## Run the shared Android and iPhone app

`my_mobile_app` is now the app for both platforms, with the same screens, navigation, account flow and logo. The older `Vulithuba` SwiftUI project is retained as a legacy prototype; running it will restore the old interface.

Start the backend, then run from `my_mobile_app`:

```bash
../.tools/flutter/bin/flutter run --release -d <device-id> --dart-define=VULITHUBA_URL=http://192.168.0.3:3000
```

The phone and Mac must share Wi-Fi while using the local address. For iPhone development, open `my_mobile_app/ios/Runner.xcworkspace`. Its bundle identifier and team match the previously installed Vulithuba iPhone app. Use your hosted HTTPS website for access outside this network.

## Production deployment

The Node.js server must be deployed alongside the static files. Configure the domain and reverse proxy so `/api/*` routes reach `server.js`. Do not use production reset links until the API and reset page are deployed together.

### HTTPS deployment with Docker

Use a server with Docker Compose and a domain pointing at that server. This deployment runs one Node.js instance with a persistent SQLite volume; Caddy provides HTTPS. Open ports 80 and 443 on the hosting firewall.

1. Copy `.env.production.example` to `.env.production` on the server. Set `DOMAIN` to the public hostname. For a new database, set a unique `ADMIN_INITIAL_PASSWORD` of at least 16 characters; add server-only mail/payment settings as needed.
2. Run `docker compose --env-file .env.production up -d --build`.
3. Check `https://YOUR-DOMAIN/api/health` and test login and registration.
4. Rebuild both apps from `my_mobile_app` using `--dart-define=VULITHUBA_URL=https://YOUR-DOMAIN` and reinstall them. The installed Android and iPhone apps use this shared Flutter project; changing the legacy SwiftUI project's plist does not update them.

If retaining current accounts and your changed admin password, migrate a verified SQLite backup into the `app-data` volume before first startup. Do not copy a live database file; use SQLite's backup API or stop the local server first. A new empty database does not contain your existing accounts. Keep database backups private and never commit them. Startup now preserves existing admin passwords. Remove `ADMIN_INITIAL_PASSWORD` after first initialization. Do not remove the persistent volume during upgrades.

The Docker image contains only the server and public web files. Secrets and the database are excluded from the image and static routes. Production session cookies require HTTPS.

### Removing the laptop dependency

The currently installed apps use `http://192.168.0.3:3000`, which is hosted by the Mac. They stop loading when the Mac sleeps or the phone leaves that Wi-Fi. Deployment files alone do not provide an online server.

Deploy the website and API together to an always-on host with persistent database storage, migrate a verified database backup to retain accounts and the changed admin password, then build updated apps with the real public HTTPS URL. Verify login, registration, scrolling, and account pages on both phones over mobile data while the Mac is shut down. Do not use a tunnel to the Mac as the permanent backend: it still depends on the laptop.

### Managed hosting on Render

`render.yaml` defines a single paid Node.js service with a 1 GB persistent SQLite disk, health checks, and Gmail SMTP configuration. Applying this Blueprint creates billable hosting resources; review the plan cost in the Render dashboard first. The free plan cannot retain the SQLite database or send Gmail SMTP mail.

Connect your repository to Render and apply the Blueprint after the deployment changes have been pushed. Enter the SMTP values privately in Render's environment configuration. Use a unique initial admin password of at least 16 characters for a new database. The backend uses Render's assigned HTTPS URL automatically through `RENDER_EXTERNAL_URL`; set `APP_URL` only if using your own domain.

To retain the current accounts and changed admin password, transfer a consistent private SQLite backup and restore it to `/var/data/vulithuba.db` while the hosted service is stopped. Do not upload `.env` or the database to GitHub. Keep the backup private. Remove the bootstrap password after initialization. Verify `/api/health` and email authentication before rebuilding and installing both phone apps with the actual hosted HTTPS URL.

No hosted URL is assigned until a Render account deploys the service. The phone apps still point to the Mac until they are rebuilt and installed with that URL.

## Infobip SMS verification

In `.env`, add `SMS_PROVIDER=infobip`, `INFOBIP_BASE_URL` (your HTTPS API origin from the Infobip portal), `INFOBIP_API_KEY` (with `sms:message:send` permission), and `INFOBIP_SENDER` (an approved sender; Infobip's trial sender is `ServiceSMS`). Keep credentials on the backend only. Restart the server after configuring them. The default provider becomes Infobip when all three Infobip settings are present, unless `SMS_PROVIDER` is explicitly set.

Select SMS when registering. Use an international number such as `+27821234567`. Infobip trial accounts can send only to their verified recipient. The server generates a six-digit code, stores its hash, and enforces a ten-minute expiry and five verification attempts. This integration uses Infobip's SMS API, not its managed 2FA API. A successful API response means the message was accepted, not that it reached the handset. If sending fails, configured email delivery is used as a fallback; failed delivery never activates an account when a delivery provider is configured or the server runs in production.

No live SMS is sent by the automated tests. Infobip credential validation and delivery still require your account settings and an explicitly requested test recipient.

## BulkSMS verification

BulkSMS is supported as another SMS provider using its JSON REST API. Generate an API token in your BulkSMS account under Settings > Developers > API Tokens, then fill `BULKSMS_TOKEN_ID` and `BULKSMS_TOKEN_SECRET` in `.env`. Set `SMS_PROVIDER=bulksms` to select it explicitly, and restart the backend. If no provider is specified, complete BulkSMS credentials take precedence over Infobip and Twilio. A BulkSMS token is required; the account login password is not used. Ensure the account is enabled for the destination and has sufficient message credit.

Phone numbers must use international format, such as `+27663820665`. The app's existing SMS verification choice, code expiry, attempt limits and email fallback continue to apply. Successful submission means BulkSMS accepted the message; consult delivery logs to confirm handset delivery. No sender field or Infobip API URL is needed for this integration. Keep token credentials on the server only. Both phone apps use the backend, so adding a provider does not require rebuilding them.

Provider documentation: https://www.bulksms.com/developer/json/v1/

## Registration validation

The website and both phone apps use the same registration page and API. `registration-validation.js` validates every required field on both the browser and server, including phone format, password confirmation and allowed plan/payment/verification selections. The form shows field-specific errors, preserves values on failure and prevents duplicate in-flight submissions.

The API validates and checks duplicate normalized emails before sending verification. After successful delivery, account and verification-code records are inserted in one database transaction. A second duplicate check and SQLite guards prevent concurrent registrations using the same email, ignoring case and surrounding whitespace. Delivery or database failures do not retain a newly created account. Existing accounts are preserved. A 201 success response is sent only after the transaction commits; the account remains pending until its code is verified. Local development with no delivery providers retains its test-only activation behavior.

Reload the registration page after updating the backend; neither phone app needs a binary rebuild for these website changes. Tests cover invalid fields, no-save failures, duplicate and concurrent requests, rollback, retained form values, and double submission without sending real messages.

Vonage Verify: set `VONAGE_API_KEY` and `VONAGE_API_SECRET`. When `SMS_PROVIDER` is unset, configured Vonage credentials select Vonage Verify. It generates a six-digit SMS code; the backend stores its request ID and validates the code with Vonage (three attempts, ten-minute expiry). Failed SMS requests fall back to configured email. An active SMS request must expire before another SMS is requested; email remains available. Existing local verification codes remain valid after switching providers. General SMS notifications are not supported by this Verify integration.

Login requires password authentication followed by SMS or email verification. Codes expire after ten minutes, allow three attempts with Vonage or five with local codes, and can only create one session. New requests have a one-minute cooldown. The default administrator email placeholder uses `ADMIN_VERIFICATION_EMAIL`, or the configured `SMTP_USER`; customer codes use the saved account contact details. Password changes and resets invalidate pending login challenges.

SMSPortal: configure `SMS_PROVIDER=smsportal`, `SMSPORTAL_CLIENT_ID` and `SMSPORTAL_API_SECRET`. Enable the REST API channel in SMSPortal. The backend sends locally generated six-digit registration and login codes through the v3 BulkMessages API. Provider acceptance is not a handset delivery confirmation; verify live delivery before rollout. Credentials remain backend-only.

ClickSend: set `SMS_PROVIDER=clicksend`, `CLICKSEND_USERNAME` and `CLICKSEND_API_KEY`. SMS registration and login use the SMS API; the backend checks both overall and individual message acceptance before storing a new code. Queue acceptance does not confirm handset delivery. Trial credits and account/country restrictions apply.
